# 创意素材（Creative Assets）设计文档

> 状态：**Phase 1 已实现并通过验证** · 范围：静态图（不含视频）
> 关联：[Apple 素材最佳实践](https://developer.apple.com/app-store/asset-best-practices/) · [Creative assets specifications](https://developer.apple.com/help/app-store-connect/reference/app-information/creative-assets-specifications)
>
> 实现与本文档的差异见 §11「实现记录」。

---

## 1. 背景与目标

iOS 27 / iPadOS 27 起，App Store 新增两个**创意素材（Creative Assets）**坑位：标题图（Product Page Header）与搜索结果图（Search Results）。它们与截图、预览视频**并列而非替代**，用于表达品牌、季节性内容与新功能，而非展示 App 在用状态。

**目标**：在 App Preview Studio 中新增一个独立的「创意素材」工作台，生成符合 Apple 硬性规格（精确像素、无 alpha 通道、关键元素在安全区内、合规）的图片素材。

**非目标（本期不做）**：视频导出、设备裁切模拟器、In-App Event 素材、Asset Library API 对接。

## 2. 官方规格（已核验）

### 2.1 尺寸与格式

来源：Apple 官方 Creative assets specifications 页面表格。

**官方表格中每个 Placement 单元格横跨 2 个子行**（HTML 为 `row-span-2`），第二个子行是「16:9 · 5244 × 2950 · 仅 PNG」，**同时挂在两个坑位下**。因此实际结构是 **2 个坑位 × 各自 2~3 种尺寸**：

| 坑位 | 比例 | 图片尺寸 | 格式 | 视频 |
|:--|:--|:--|:--|:--|
| **标题图** Product Page Header | 21:9 | **3840 × 1646**（固定） | .jpeg / .jpg / .png | 3840×1646，5–30s，30/60fps |
| ↑ 同一坑位 | 16:9 | **5244 × 2950**（固定） | **仅 .png** | — |
| **搜索结果图** Search Results | 3:2 | **3840 × 2560** 或 **1920 × 1280** | .jpeg / .jpg / .png | 同尺寸，5–30s，30/60fps |
| ↑ 同一坑位 | 16:9 | **5244 × 2950**（固定） | **仅 .png** | — |

去重后共 **5 个尺寸选项**（5244 × 2950 在两个坑位下各出现一次）。

硬性约束：

- **图片不能含 alpha 通道或任何透明**（导出管线已修复，见 §7）
- 一张图通吃 iPhone / iPad、横屏 / 竖屏，**没有分机型尺寸**
- 仅对运行 iOS 27 / iPadOS 27+ 的 iPhone 与 iPad 应用生效
- 5244 × 2950 同时出现在两个坑位下，意味着**同一份文件可以同时填两处**（对应 ASC 版本页的「Use header asset in search results」）。它不是第三个独立坑位，而是两个坑位**共用的一个尺寸**（代码中标记 `universal`）

> ⚠️ 本文档早期版本把 5244 × 2950 建模成独立的第三个坑位「通用素材」，这是对规格表的误读（把跨两行的表格读成了三个 placement），现已按官方表格结构修正。

### 2.2 安全区（Apple 官方模板实测）

Apple **从不公布**安全区像素值，官方只有定性规则：

> *"Design key elements with a safe area in mind to accommodate different devices and orientations. Be sure your focal point artwork is within the center of your composition to prevent any unwanted clipping."*

数值藏在官方设计模板里。我们从 **Apple 自己的 Sketch 文件**中直接解析得到：

```
https://devimages-cdn.apple.com/design/resources/download/app-store/creative_assets-templates.sketch
```

该文件包含 3 个画板，与官方规格表逐一吻合。

**实测结果：**

| 画布 | 用于坑位 | 安全区 (x, y, w, h) | 边距 上/右/下/左 | 面积占比 | 来源 |
|:--|:--|:--|:--|:--|:--|
| 3840 × 1646 | 标题图 | **(1097, 493, 1646, 661)** | 493 / 1097 / 492 / 1097 | 17.2% | 实测 |
| 3840 × 2560 | 搜索结果图 | **(836, 765, 2168, 1030)** | 765 / 836 / 765 / 836 | 22.7% | 实测 |
| 5244 × 2950 | **两个坑位共用** | **(1921, 660, 1402, 962)** | 660 / 1921 / 1328 / 1921 | **8.7%** | 实测 |
| 1920 × 1280 | 搜索结果图 | **(418, 383, 1084, 515)** | 383 / 418 / 382 / 418 | 22.7% | 推导 |

**1920 × 1280 的推导依据**：Apple 模板只提供了 3840 × 2560 的安全区。两者**同为 3:2**，而裁切行为由宽高比与设备决定，因此同一比例下安全区在画布上的**相对位置完全一致**，按 0.5 等比缩放即可精确还原：

- 水平：`418 + 1084 = 1502 = 1920 − 418` ✓ 仍完美居中
- 垂直：`765 × 0.5 = 382.5` 取整到 383，产生 1px 误差，可忽略

**校验结果（三重验证通过）：**

1. **对称性**：三个实测画布的安全区**水平方向完美居中**（左/右边距完全相等）；标题图与搜索结果**垂直方向也居中**。
2. **5244 × 2950 垂直偏上**：上边距 660 / 下边距 1328，安全区中心比画布中心**偏上 334px**。⚠️ 「肉眼看着居中」的排版在共用尺寸上是错的，这是最隐蔽的坑。
3. **跨源一致**：与三家第三方独立测量（storeheader.com、blakecrosley.com、Stoot）的结果逐像素一致；并用 Apple 的 Photoshop 模板独立确认了画布尺寸（3840×1646 / 5244×2950）。

### 2.3 解析模板时的陷阱（务必注意）

Sketch 文件里的 **group frame 字段不可信**，存在未同步的过期值：

- Header 画板的 `Artwork` 组 frame 写的是 `1658×1060`，但它内部的 `Background` 矩形实际是 `3840×1646`。
- Universal 画板的 `Art Safe Area` 组 frame 写的是 `1658×1060`（与 Search Result 的组**完全相同的数值**，明显是复制残留），但其内部叶子矩形 `Art Area/Art Safe Area` 实际是 `1402×962`。

**正确取法**：用父组的 `x/y` 作为原点（相对画板），用组内**叶子矩形**的 `width/height` 作为尺寸。若直接读组 frame，5244×2950 画板会得到错误的 1658×1060。

### 2.4 全部官方模板地址

页面上的 8 个模板链接均为 `/go/?id=...` 跳转，已解析：

| 工具 | 用途 | 直链 |
|:--|:--|:--|
| Figma | Universal | `…/app-store/creative_assets-templates.fig` |
| Photoshop | Header | `…/app-store/creative_assets-product_page_header_template-static.psd` |
| Photoshop | Universal | `…/app-store/creative_assets-universal_asset_template-static.psd` |
| Photoshop | Search results | `…/app-store/creative_assets-search_results_template-static.psd` |
| Pixelmator | Header / Universal / Search results | `…/app-store/creative_assets-product_page_header_template-static.pxd` 等 |
| Sketch | 三个画板合一 | `…/app-store/creative_assets-templates.sketch` |

（前缀均为 `https://devimages-cdn.apple.com/design/resources/download`）

> 注：`-static` 后缀的 PSD 是**已拼合的无图层**文件，只含烘焙后的像素，不含可解析的图层信息。因此**安全区只能从 Sketch 文件取**。

### 2.5 格式与尺寸的处理决策

| 项 | 官方说明 | 本工具的处理 |
|:--|:--|:--|
| 5244 × 2950 的格式 | 规格表该行明确写 `.png`（其他行是 `.jpeg/.jpg/.png`） | 按 **png-only** 实现，并在尺寸卡片上标注「仅支持 .png」 |
| 3840×1646 / 3:2 的格式 | 规格表写 `.jpeg/.jpg/.png` | 统一导出 **PNG**——三处格式均合法，且无损、无压缩伪影，中文小字更清晰 |
| 3:2 是否只认这两个分辨率 | 规格表给的是 min/max 区间（1920×1280 ~ 3840×2560）而非枚举 | 提供 **3840×2560** 与 **1920×1280** 两个端点值；**不开放自定义**，避免区间内未列举的值被拒 |

> 早期曾提供过 `2880×1920` 这个中间值。因其既非规格表列举值也无实测安全区依据，已移除。

## 3. 交互设计

### 3.1 核心原则：两个工作台，不是一个工作台的两个尺寸

两者不是同一件事，塞进同一个面板列表只会互相拖累：

| | App 预览截图 | 创意素材 |
|:--|:--|:--|
| **表达什么** | 展示 App **在用**（Apple 强制要求） | 表达**品牌 / 季节 / 新内容** |
| **几何** | 竖屏设备尺寸，宽高比 ≈ 0.46 | 超宽横幅，宽高比 2.33 / 1.78 / 1.50 |
| **设计规则** | 信息密度高是优点 | Apple 明令 *"visually dense or cluttered assets dilute your impact"* |
| **素材输入** | 必须有 App 截图 | **常常完全不需要截图**，纯品牌排版也合法 |

由此推出一条硬约束：**现有的 6 个截图版式不可复用到创意素材**。「多机错落」（3 台手机 + 主副标题 + logo）恰恰是 Apple 对标题图警告的「视觉过载」样板。创意素材必须建立独立的版式体系。

### 3.2 整体框架

```
┌──────────────────────────────────────────────────────────────────────┐
│ ▣ App Preview Studio  [项目名]       3840 × 1646   [批量ZIP] [导出PNG] │ ← 顶栏（共享）
├──────────────────────────────────────────────────────────────────────┤
│  ▣ App 预览截图    │   ◇ 创意素材         安全区 1646×661 · ✓ 4/4     │ ← 工作台切换条
├───────────────┬──────────────────────────────────────────────────────┤
│ ① 坑位        │                                                     │
│ ② 变体组      │                                                     │
│ ③ 素材上传    │                  画布预览区                         │
│ ④ 版式        │                                                     │
│ ⑤ 主题        │                                                     │
│ ⑥ 品牌        │                                                     │
│ ⑦ 文案        │                                                     │
│ ⑧ 安全区检查 ⭐│                                                     │
│ ⑨ 合规检查   ⭐│                                                     │
│ ⑩ 项目        │                                                     │
└───────────────┴──────────────────────────────────────────────────────┘
```

**为什么切换条放第二行而不是塞进顶栏**：顶栏已有 logo / 项目名 / 尺寸徽章 / 两个按钮，再塞分段控件会很挤，且会让「项目名」的归属变模糊。第二行既能容纳清晰的 2 段切换，右侧还空得出位置放**当前模式的上下文信息**——这在截图模式下没有意义，正好强化两种模式的差异。

### 3.3 模式切换

- **2 段**：`App 预览截图` / `创意素材`。3 个坑位放在左侧面板顶部，因为坑位与截图模式的「导出尺寸」是同一层级（项目级设置）。
- **首次访问默认「App 预览截图」**，与现状行为逐像素一致。
- 记忆上次所在模式（localStorage key `app-preview-studio.mode`），下次直接回到该模式。
- 切换是即时的，**不重置任何数据**：两个 store 常驻，图片与配置互不干扰。

### 3.4 坑位（项目级）

坑位决定画布尺寸，与截图模式的 `sizeId` 同构。

| 卡片内容 | 说明 |
|:--|:--|
| 标题图 · 21:9 · 3840×1646 | 进入产品页的第一眼，表达品牌与季节内容 |
| 标题图 · 16:9 · 5244×2950 | 与搜索结果图共用，安全区最小（8.7%），最考验排版 |
| 搜索结果图 · 3:2 · 3840×2560 | 搜索列表里的首图，建议直观展示产品用途 |
| 搜索结果图 · 3:2 · 1920×1280 | 同上，较小尺寸（安全区由 3840×2560 等比推导） |
| 搜索结果图 · 16:9 · 5244×2950 | 与标题图共用 |

**尺寸选择方式**：两个坑位各自列出全部支持尺寸，点击即同时切换坑位与画布。5244 × 2950 在两处都会出现，标注「一份文件同时填标题图与搜索结果图」。

**切换尺寸不丢数据**：字号以「画布宽度比例」存储，3840 宽 → 5244 宽是 1.365 倍，画布显示宽度同为 1.365 倍，**屏幕上视觉大小完全不变**。版式参数以**安全区**为基准，同样等比缩放。用户在任意尺寸间切换都是无损的视觉转换，无需重调任何参数。

### 3.5 变体组（条目级）

对应截图模式的「截图组」，但语义不同：

- **为什么叫变体**：呼应 Asset Library 工作流——预先备好多套素材（如夏季版 / 冬季版 / 新版本），审核通过后上线时直接替换，**无需提交新版本**。这正是 Asset Library 存在的意义。
- **上限 12**（截图模式为 10），且**主体图可以留空**（纯品牌排版也合法）。
- 交互完全复用 `ScreenshotList.vue` 的缩略图条 + 新增/复制/删除模式，只是文案改为「变体」。

### 3.6 素材上传

复用 `ImageUploader.vue`，但**文案与语义不同**：

- 截图模式：`上传 App 截图`（拖拽 / ⌘V 粘贴），未上传时提示「当前显示的是示例界面」
- 创意素材：`上传主体图（可选）` + 副标题「不上传也可以，纯品牌排版同样合法」

主体图在版式中作为一个**自由视觉元素**出现（带可调圆角的圆角矩形），可以出血、可以压边。

> **关于取消手机边框面板**：按决策，创意素材模式**不提供手机边框（Phone Frame）面板**。因此版式体系从「手机 + 文字」改为「图片 + 文字」。这更贴合 Apple 对标题图的指导（表达品牌而非展示在用状态）。
> 需注意 Apple 对搜索结果的指导是 *"Showcase the firsthand experience"*——若搜索结果素材需要展示界面，用户上传真实 UI 截图即可满足，无需手机 mockup。

### 3.7 版式（几何以安全区为基准）

**关键设计决策：所有位置参数相对「安全区」定义，而非画布边缘。** 背景与出血元素仍相对画布，允许自由发挥。

| 版式 | 描述 | 参数（相对安全区） |
|:--|:--|:--|
| **居中主张** | logo + 主标题 + 副标题居中于安全区，无图 | 文本纵向位置、宽度 |
| **左文右图** | 文案在安全区左侧，主体图在右侧并可出血 | 文本宽度、文本位置、图尺寸、图位置、圆角 |
| **上文下图** | 文字占安全区上半，主体图在下半出血 | 文本位置、图尺寸、出血程度 |
| **纯品牌** | 仅 logo + 主张 + 背景，无图 | 文本纵向位置、宽度 |

这样做的收益：**版式天生不会越界**。越界只可能来自用户把文案写太长或字号调太大——而那正是安全区检查该抓的。

### 3.8 安全区检查 ⭐（核心差异化）

安全区 = Apple 所有裁切方式的**交集**。只要关键元素都在里面，任何设备任何方向都不会裁掉。因此**逻辑上它已经解决了约 80% 的正确性问题**——这也是本期不做设备裁切模拟器的理由（模拟器解决的是「能看到损失多少」的体验增强，不解决正确性）。

**三层反馈：**

**① 画布叠加层**
- 安全区外的区域压一层极淡遮罩（降低对比）
- 安全区边界 1px 虚线
- 越界元素描红边 + 半透明红色高亮
- 眼睛图标可切换叠加层（默认开启）

**② 面板列表**
逐元素校验，✓ / ✗ 标注具体超出量：

```
品牌 Logo        ✓
主标题           ✗  超出安全区 214px（下）
副标题           ✓
主体图           ✓
```

点击任意行 → 画布上对应元素闪烁一次定位。

**③ 顶栏徽章**
`安全区 ✓ 4/4`（绿） / `⚠ 2 项越界`（红），点击滚动到面板。

**测量方案**：用 `offsetWidth` / `offsetHeight` 取真实布局盒——**不受 CSS transform 影响**，因此预览区缩放到 0.2 时依然测得准确——与安全区矩形求交。无需新增测量机制，与现有架构天然契合。

> **顺带解决一个真实痛点**：标题图安全区只有 1646px 宽，主标题按 `0.05 × 3840 = 192px` 计算，一行仅约 8 个汉字，**2 行封顶**。截图模式那种长文案切过来必然撑爆。安全区检查会自动发现「文本换行后撑出安全区」，并可显示每行实际容量——中文用户不必自己算。

### 3.9 合规检查 ⭐（核心差异化）

Apple 对商店素材的硬性规则，实时扫描文案 + 品牌名 + 主体图文案：

| 规则 | 触发示例 | 依据 |
|:--|:--|:--|
| 禁止价格 / 折扣 | `¥` `$` `￥` `% off` 限时 折扣 立减 免费 特价 | Don't include specific pricing, discounts |
| 禁止网址 | `http` `www.` `.com` | Don't include website URLs |
| 禁止版权符号 | `©` `®` `™` | …copyright symbols |
| 禁止奖项 / 榜单 | `Editor's Choice` `App of the Day` `Game of the Day` `最佳应用` `年度` | Avoid unverifiable claims |
| 4+ 内容分级 | 少量敏感词弱提示 | Assets must meet a 4+ age rating |

全部通过显示绿色 ✓；命中则高亮对应文本并给出改写建议。**竞品目前都只是把这几条写成文字说明，无人做成机器校验**——这是最实在的差异化点。

### 3.10 空状态引导

进入创意素材模式后必须明确「这不是截图」：

- 切换条右侧提示：`标题图 · 表达品牌与季节内容，不是 App 截图`
- 首次进入自动展开「坑位」面板
- 画布占位沿用现有 `PlaceholderScreen`，文案改为 `上传主体图（可选），或直接用纯品牌排版`

## 4. 数据模型

```ts
// src/constants/placements.ts
export interface CanvasOption {
  width: number
  height: number
  label: string
}

export interface Placement {
  id: 'header' | 'search' | 'universal'
  name: string
  /** 比例标签，如 '21:9' */
  aspect: string
  /** 该坑位支持的画布尺寸（标题图 2 种、搜索结果图 3 种） */
  canvasOptions: CanvasOption[]
  /** 关键元素安全区（来自 Apple Sketch 模板实测） */
  safeArea: { x: number; y: number; width: number; height: number }
  /** 该素材可填的坑位 */
  fills: Array<'product-page-header' | 'search-results'>
  /** 坑位用途一句话说明 */
  note: string
  /** 特殊提示（如 5244×2950 安全区偏上） */
  warning?: string
}
```

## 7. 已完成：导出 alpha 通道修复（前置项）

新素材规格第一条就是 *"Images can't include alpha channels or transparencies"*，因此先修复了既有的导出问题。

**根因**：`modern-screenshot` 即使传入 `backgroundColor`，输出 PNG 始终为 `colorType 6 (RGBA)`。像素确实全不透明（实测 `minAlpha = 255`，0 个半透明采样），但**文件格式层面带 alpha 通道**。原 `verify-export.mjs` 仅用 `sips` 校验像素宽高，故长期未被发现。

**修复过程中的关键发现**——Chrome 对 PNG 编码的策略差异（Chrome 155 实测）：

| 方案 | colorType |
|:--|:--|
| `toDataURL('image/png')` + `alpha:false` 画布 | 6 ❌ |
| `putImageData` + `toDataURL` | 6 ❌ |
| 默认 alpha 画布 + `toDataURL` | 6 ❌ |
| **`toBlob('image/png')` + `alpha:false` 画布** | **2 ✅** |
| `OffscreenCanvas.convertToBlob` | 2 ✅ |

`toDataURL` 对 PNG **硬编码输出 RGBA**，不理会 context 的 alpha 设置；只有 `toBlob` 会尊重。第一版修复用了 `toDataURL`，被新增的断言直接测出 FAIL。

**改动**：
- `src/composables/useExport.ts` — 新增 `flattenToOpaquePng()`，导出末端重绘到 `alpha:false` 画布并用 `toBlob` 编码
- `scripts/verify-export.mjs` — 新增直读 PNG IHDR 的 colorType 断言（真正防回归的那道防线）
- `docs/sample-*.png` — 重新生成，现为 `colorType 2 (RGB)`

**验证**：`verify:export` / `verify:workflow` / `verify:fonts` / `verify:panel` 全部通过，`npm run build` 通过。附带收益：去掉 alpha 后样张体积下降约 18–20%。

## 12. 修正：字号基准从「画布宽度」改为「安全区宽度」

用户反馈「主副标题太容易换行，一行不够用」。经实测定位到根因并修正。

### 根因

初版把字号定义为「**画布宽度**的比例」（`fontSize = size × canvasW`）。这对截图模式成立（画布本身就是排版容器），但对创意素材是错的：**安全区才是排版容器**，而安全区占画布宽度的比例在各尺寸间差异极大：

| 画布 | 安全区宽 | 占画布 |
|:--|--:|--:|
| 3840 × 1646 | 1646 | 42.9% |
| 3840 × 2560 | 2168 | 56.5% |
| 5244 × 2950 | 1402 | **26.7%** |
| 1920 × 1280 | 1084 | 56.5% |

同一份参数（`size = 0.034`）在页头上得到 131px 字号（合理），在 5244×2950 上却得到 **178px**（过大），而后者安全区只有 1402px 宽 —— **每行仅能放下 7 个汉字**。

### 实测（修正前）

| 画布 | 安全区W | 标题字号 | 每行可容 |
|:--|--:|--:|--:|
| header 3840×1646 | 1646 | 131px | 11 字 |
| header 5244×2950 | 1402 | 178px | **7 字** |
| search 3840×2560 | 2168 | 131px | 15 字 |
| search 1920×1280 | 1084 | 65px | 15 字 |
| search 5244×2950 | 1402 | 178px | **7 字** |

### 修正

在 `SharedAssetStore` 增加 `designWidth`：

- 截图 store → `canvasSize.width`（**行为完全不变**）
- 创意素材 store → `safeArea.width`

`TextLayer` 收到的 `canvasW` 改为 `safe.width`，于是**字号、行距、logo 尺寸、字间距全部按安全区等比缩放**。同时按新基准重标定默认值（主标题 0.08 / 副标题 0.032 / logo 0.055 / 行距 0.02）。

### 实测（修正后）

| 画布 | 安全区W | 标题字号 | 每行可容 |
|:--|--:|--:|--:|
| header 3840×1646 | 1646 | 132px | **12 字** |
| header 5244×2950 | 1402 | 112px | **12 字** |
| search 3840×2560 | 2168 | 173px | **12 字** |
| search 1920×1280 | 1084 | 87px | **12 字** |
| search 5244×2950 | 1402 | 112px | **12 字** |

五个尺寸的每行容量**完全一致**，重灾区的 7 字 → 12 字。

### 附带收益

- 面板里的 px 读数（字号 / 行距 / logo 高度）现在反映真实渲染值 —— 改用 `designWidth` 之前，创意素材下这些数字是按画布宽度算的，与画布实际渲染对不上。
- 切换尺寸时排版密度不再突变，用户无需重新调参。
- 已加断言 `五个尺寸下标题每行容量一致`，防止将来有人改回按画布宽度计算。

### 验证

## 13. 修正：预览视口在切换尺寸后未重算缩放

用户反馈「每次切换到 5244 那一档，右边画布区域只能看到很少的一个局部」。

### 根因

`CreativeStage` / `PreviewStage` 的缩放值原先只在**宿主容器** ResizeObserver 触发时重算：

```ts
ro = new ResizeObserver(fit)
ro.observe(hostEl)
```

但切换画布尺寸**不会**改变宿主尺寸 —— 于是缩放值一直沿用上一次的。

实测（1680 视口，宿主 1360×954）：

| 操作 | 缩放 | 画布实际占位 | 可见比例 |
|:--|--:|--:|:--|
| 初始 3840×1646 | 0.325 | 1248×535 | 109% × 178% |
| → 1920×1280 | 0.325（**未重算**） | 624×416 | 218% × 229% ← 该放大却没放大 |
| → 5244×2950 | 0.325（**未重算**） | 1704×959 | 80% × 99% ← 被裁掉 |

从更小的画布切过来更严重：`1920×1280` 的 fitScale 是 0.65，切到 `5244×2950` 后仍是 0.65，画布被撑到 **3409×1918**，而宿主只有 1360×954 —— 横向只看得见 40%。

### 修正

抽出 `composables/useStageViewport.ts`，两个工作台共用：

1. **画布尺寸变化时重新「适应窗口」并归零平移**（核心修复）；
2. 在此之上提供用户缩放与平移：
   - 右下角控件 `−` / `适应` / `1:1`（`ScaleZoomBar`）
   - `⌘/Ctrl + 滚轮`以指针为锚点缩放（锚点下的内容在缩放前后保持不动）
   - 普通滚轮 / 拖拽平移，平移量夹在内容边界内 —— 画布不会被拖丢
   - 缩放 = `fitScale（窗口自适应） × zoom（用户档位）`，所以窗口 resize 时用户的相对缩放不跳变
3. `1:1` 档位**对准安全区**而非画布中心：5244×2950 的安全区只占画布 26.7% 宽且垂直偏上 334px，对准画布中心等于对准一片空白。

顺带修掉了同样的截图画布问题（横屏切换时画布偏小），以及放大时引导气泡遮挡画布的问题（仅在「适应」档位显示）。

### 验证

`verify:creative` 新增 6 项断言（37 → 38 项，含子项共 6 条新增）：

- 切换尺寸后画布始终完整可见（缩放随尺寸重算）
- 「1:1」档位 = 100%，且画布按原始像素 5244×2950 渲染
- 1:1 视口对准安全区（偏移 Y = 334，而非 0）
- 「适应」回到完整可见
- 拖拽可平移，且被夹在内容边界内（偏移 = 上限 1942, 998）

导出管线未受影响：`npm run docs:capture` 重新生成后，`docs/sample-*.png` **逐字节未变**，只有 `docs/ui.png`（界面截图）更新。

## 14. 修正：上传主体图后画布毫无变化

用户反馈「上传的主体图是干什么的，为什么我上传了后在画布上完全看不到，是不是一个 bug」。

### 现象与根因

不是「图没加载」——直接调 `setLayout('text-left')` 后图片立刻出现（991 × 661）。
真正的原因是**默认版式「居中主张」的 `resolve` 写死了 `image: noImage()`**，它根本不绘制主体图：

| 版式 | 是否绘制主体图 |
|:--|:--|
| 居中主张（默认） | ❌ `resolve` 直接返回 `image: null` |
| 左文右图 / 上文下图 / 满幅图底 | ✅ |

于是完整链路上**没有任何一环告诉用户真相**：

1. 上传 → 面板显示「已导入」+ 缩略图（看起来成功了）
2. 画布纹丝不动
3. 版式卡片没有标记，看不出「居中主张不用图」
4. 画布上的引导气泡又在有图后自动隐藏 → 连「还没上传」的暗示都没了

### 判定：版式意图合法，交互缺失不合法

「居中主张不画图」本身是有正当理由的——Apple 明确建议
"focus on a single, clear idea; visually dense or cluttered assets dilute your impact"，
纯排版版式正是为此存在。**这个设计约束保留。**

但「上传后毫无反馈」不是设计约束，是交互缺陷：用户上传图片只有一个合理预期——
**我要看到它**。因此修在交互层，而不是让居中主张去画图。

### 修正

1. **版式显式声明 `usesImage`**（`data/bannerLayouts.ts`）
   必须声明式写出，不能靠读 `resolve` 结果推断 —— 面板要在「有图但版式不用图」时
   提前提示，而那时没有可信的 ctx 可算。

2. **上传自动换版式**（`stores/creative.ts` 新增 `setImage()`）
   当前版式不画图时自动切到第一个 `usesImage` 的版式。点击选择与拖拽/粘贴
   两条上传路径统一走这个 action，避免行为不一致。

3. **画布上给出口**（`CreativeStage.vue`）
   「主体图已上传，当前版式不展示它」+ 一键切到用图版式 + 可忽略（切换版式即复位）。
   提示必须出现在画布上——用户正盯着那里。

4. **版式卡片标注「用图 / 纯排版」**（`BannerLayoutPicker.vue`）
   让这件事在**选版式时**就可见，而不是等上传后才发现。

5. **上传面板常驻状态行**（`CreativeImageUploader.vue`）
   `✓ 当前版式「左文右图」会展示主体图` / `⚠ 当前版式「居中主张」不展示主体图`
   + 一键切换按钮。不用瞬时状态，永远反映当前事实。

### 验证

`verify:creative` 38 → 46 项，新增 8 条：

## 15. 图片裁剪工作台（第三个工作台）

### 定位：不做设计，只做裁剪

前面两个工作台都是**从零生成**素材（文案 + 版式 + 主题 + 品牌）。
但真实流程里有另一类需求：**图已经画好了**（可能来自设计师的 Figma、可能来自上一年的素材、
可能就是一张实拍图），只需要按官方比例裁开、导出成合法文件。

这类需求跟前两个工作台是**互斥**的：用户已经定了设计，工具不该再给他主题、文案、
品牌这些入口 —— 每多一个入口，就多一次「我是不是该在这里改点什么」的犹豫。
因此裁剪工作台是**独立的一档**，面板只有：图片 / 坑位与尺寸 / 构图 / 安全区 / 批量导出 / 项目。

隔离方式与创意素材一致（`§5`）：
独立 store（`stores/crop.ts`）、独立 localStorage key（`app-preview-studio.crop.v1`）、
独立命名空间（时间戳 + 命名空间，避免「无图也导出空白」）。
不伪造 `SharedAssetStore` —— 裁剪没有主题 / 文案 / 品牌，硬造一个空壳会把边界弄糊（`AGENTS.md`）。

### 数据模型：构图存相对量，不存像素

```ts
interface CropItem {
  zoom: number      // 相对「刚好铺满画框」的倍数，∈ [1, 4]
  offset: { x: number; y: number }  // 归一化到「多余空间」，各轴 ∈ [-1, 1]
  width: number     // 源图像素尺寸（用于画质判断）
  height: number
}
```

存相对量的**直接收益**：切画框尺寸时构图意图自动保留。
在 21:9 上把画面挪到「看右边」，切到 3:2 依然是「看右边」。

实测（同一份 2400 × 1600 源图，zoom = 1.8，offset 居中）：

| 画框 | 可见源图水平区间 | 可见源图垂直区间 |
|:--|:--|:--|
| 3840 × 1646（21:9） | x ∈ [533, 1867] | y ∈ [514, 1086] |
| 5244 × 2950（16:9） | x ∈ [533, 1867] | y ∈ [425, 1175] |

水平区间**逐像素一致** —— 这就是「不需要重裁四遍」的量化含义。

若存像素（`offsetX: number` 表示图片左上角坐标），切画框时只能按比例硬缩放，
一旦源图与画框的比例关系变化（21:9 → 3:2 变化很大），偏移量的语义就失效了。

几何计算全部是**同步纯函数**（所以切尺寸时能立刻算出结果，不需要等图片加载）：

```
coverSize()      → 刚好铺满画框的尺寸（取宽 / 高两条约束里更大的那个）
dispSize()       → cover × zoom
slack()          → (disp - frame) / 2，两个轴各自计算
resolveCropBox() → 图片左上角 = -slack × (1 + offset)，再向外取整
```

### zoom 下限是 1，不是 0

`zoom < 1` 意味着图片缩到**盖不住画框**，会露出画框底色。
那时唯一能做的选择是替用户猜一个背景色 —— 而用户从未表达过任何背景色意图。

这不是「实现麻烦所以不做」，而是**做了就一定会产出用户没要的东西**：
一个他自己都没见过的底色会被写进导出的 PNG，且无法撤销（导出文件已经离开浏览器）。
因此 `zoom ∈ [1, 4]`：

- 下限 1 = 刚好铺满（等于 `object-fit: cover`，用户对这个语义有直觉）
- 上限 4 = 再多源图必然糊（3840 的画框放到 4 倍需要 15360px 的源图）

### 画框锁定比例，动的是图片

两种交互模型都能达到「裁剪」的目的，选择的是前者：

| 模型 | 用户操作 | 判定 |
|:--|:--|:--|
| **画框锁定比例**（采用） | 拖动 / 缩放图片 | ✅ 不可能产出比例错误的文件 —— 画框永远是官方比例 |
| 自由画框 | 拖动四条边 | ❌ 用户可以拖出一个不合法的比例，工具得在旁边不断纠正他 |

裁剪工作台的**产出契约是「比例一定正确」**，把这件事从「用户要做对」变成「工具保证」，
是这个工作台存在的全部理由。画框尺寸因此由坑位与尺寸决定，用户不能直接拖。

### 两层缩放必须分清

画布上的滚轮有**两个**合理含义，混在一起就必然有一半时刻是错的：

| 操作 | 缩放对象 | 为什么 |
|:--|:--|:--|
| 滚轮 | **构图**（源图在框内多大） | 用户正盯着画布调裁剪，滚轮是他最自然的「放大看看」 |
| `⌘ / Ctrl + 滚轮` | **预览**（画布在屏幕上多大） | 与外层预览区的约定一致（`useStageViewport`） |

`CropStage.vue` 是**唯一**区分这两者的地方：捕获 `wheel`，
按 `metaKey / ctrlKey` 分派，然后 `preventDefault` + `stopPropagation`
（否则会同时触发宿主上的预览缩放，两层一起动）。

### 无余量的轴：锁 0，且不显示滑杆

`slack = 0` 表示该方向刚好铺满、没有可调空间（例如竖图裁 21:9 时水平方向）。
此时偏移必须锁 0 —— 否则「滑了画布不动」会被判定为 bug。

但**只锁住还不够**：滑杆留在面板上、拖了没反应，用户依然会认为是 bug。
因此该轴没有余量时**滑杆整个不显示**，改为一行说明（「水平方向已铺满」）。
这属于「用户看不到反馈」类问题（`§14` 的同类信号），按 bug 处理。

### 画质告警：裁剪最隐蔽的失败模式

裁剪不会像文字排版那样「一眼看出不对」。一张 800 × 600 的图裁成 3840 × 1646，
界面上一切正常、比例正确、导出成功 —— 但成品是**把源图放大了 4.8 倍**，
上传到 App Store 就是一张糊图。

因此导出前量出「这次构图实际用到的源图像素占画框的比例」：

```
usedSourceWidth = 源图宽 × (画框宽 / 图片绘制宽)
coverage        = usedSourceWidth / 画框宽
放大倍数         = 1 / coverage - 1
```

`coverage < 1` 时给出「⚠ 会被放大 N%，成品会糊」。
关键性质：**这个告警随构图实时变化** —— 用户放大源图（zoom ↑）会看到倍数上升，
这让他能在导出前就理解「放大」的代价，而不是导出后才被审核打回。

徽章同时出现在**画布上**（用户正盯着的地方）与**顶栏**（滑到面板底部时也看得见），
两处文案取自同一份 `useCropQuality`，不可能不一致。

### 一键全部尺寸

四个尺寸的画框比例不同，但构图意图相同，因此**逐个画框重排同一份构图**再导出：

| 坑位 | 比例 | 导出尺寸 | 文件名 |
|:--|:--|:--|:--|
| 标题图 | 21:9 | 3840 × 1646 | `{项目}_21x9_3840x1646.png` |
| 标题图 / 搜索结果图 | 16:9 | 5244 × 2950 | `{项目}_16x9_通用双坑位_5244x2950.png` |
| 搜索结果图 | 3:2 | 3840 × 2560 | `{项目}_3x2_3840x2560.png` |
| 搜索结果图 | 3:2 | 1920 × 1280 | `{项目}_3x2_1920x1280.png` |

- 尺寸按 **WxH 去重**（`allCanvasOptions()`），因此 5 个坑位选项 → 4 个文件，
  5244 × 2950 不会被导出两遍
- 通用尺寸在文件名里带 `通用双坑位` —— 用户拿到 ZIP 时不必回来查表
- 打包成 `{项目}_全部尺寸.zip`，每个条目都已剥离 alpha 通道（`§7` 的 `flattenToOpaquePng`）
- ZIP 条目名标注 UTF-8（`flag & 0x800`），中文项目名在 Windows / macOS 上都不乱码

### 安全区叠加层不进导出

裁剪工作台的安全区**仅作预览参考**（用户要判断裁剪后关键内容是否还在安全区内）。
叠加层与压暗面板在 `CropCanvas` 内由 `overlay` 开关控制，
导出宿主里固定 `:overlay="false"`（与 `CreativeCanvas` 同规则）。

这条不能靠「看代码觉得对」：`verify:crop` 用**纯色源图**导出后逐点比色 ——
576 个采样点（含四条边界）必须全部等于源图颜色。任何叠加层泄漏、
任何被外部 CSS 裁出的空白、任何亚像素缝隙露出的画框底色，都会让这条断言变红。

### 验证

`verify:crop`（现 69 项）覆盖：三档工作台切换 / 尺寸矩阵同源 / cover 几何 /
拖拽与两层滚轮 / 切尺寸构图保留 / 夹紧与锁定 / 批量导入与上限 12 /

**导出成品像素级等于源图** / 刷新恢复 / 三份项目 JSON 互不串味 /
**删除出口与空列表**（§18）。

## 16. 修正：裁剪图片被外部 CSS 截断

### 现象

`verify:crop` 的像素断言第一次跑就红了：导出成本里 6.25% 的采样点不是源图颜色，
而且是**纯白**（`[255,255,255]`）。

进一步逐像素扫描整张成品的污染分布，规律非常明确：

| 构图 | 图片绘制宽度 | 污染列数 | 污染位置 |
|:--|:--|:--|:--|
| zoom = 1（不溢出） | 3840 | **0** | — |
| zoom = 1.1 | 4224 | 192 | 最右侧 192 列 |
| zoom = 1.8 | 6912 | 1536 | 最右侧 1536 列 |

污染列数**恰好等于 `slack.x`**，换算成图片局部坐标后边界落在 **3840** —— 也就是
**画框宽度**。即：图片实际只被渲染到「画框宽度」为止，右边多出来的部分整块是空的
（空 = 透明 → `flattenToOpaquePng` 的白底显出来）。

### 根因

Tailwind preflight 给所有 `<img>` 设了：

```css
img, video { max-width: 100%; height: auto; }
```

裁剪工作台的源图**按设计必然超出画框**（铺满之后再放大），于是被这条
`max-width: 100%`（= 容器宽 = 画框宽）静默裁掉。

这正是 `AGENTS.md`「画布组件一个 Tailwind class 都不能有」那条规则的**反面**：
既然画布不能依赖外部 CSS，它就必须**显式免疫**外部 CSS。
`display: block` 早就写了（也是 preflight 的内容），但 `max-width` 漏了。

另外两个画布撞不到这条，因为它们的图片始终在画布范围内。

### 为什么只有像素断言抓得到

这个 bug 的伪装极其完整 —— 出事时下列数据**全部正常**：

- 画布 box 尺寸、位置 ✅
- `img.style.width` = `6912px` ✅（DOM 上确实是 6912）
- `img` 的 `getBoundingClientRect()` ✅
- 成品的宽高、比例、alpha 通道 ✅
- 页面上没有任何报错 ✅

唯一明确的现象是**画布右侧有一块空白**，而它看起来很像「背景色」——
如果不是纯色源图 + 逐点比色，很容易被当成设计意图而放过。

`zoom = 1` 时图片不溢出，这条 bug 完全测不出来。因此像素断言**必须跑在放大状态下**
（`verify:crop` 在导出前显式 `setZoom(1.8)`，并断言 `getComputedStyle(img).maxWidth === 'none'`）。

### 修正

`CropCanvas.vue` 的 `imageStyle` 显式写 `maxWidth: 'none'` / `maxHeight: 'none'`。
修复后 576 个采样点全部等于源图颜色。

同一批次还补了两个同类缺陷（都是「画布里的 `<img>` 少写了属性」）：

1. **`draggable="false"`** —— Chrome 默认允许拖拽 `<img>`，而 `useImageUpload`
   在 window 上监听 `drop`。在裁剪画布上拖动构图 = 拖出一张图再 drop 回来，
   凭空多导入一条（实测：导入 3 张后条目数是 4）。`PhoneFrame.vue` 早就有这个属性，
   其余画布是后补的。
2. **`onCanvasPointerDown` 里的 `preventDefault()`** —— 顺手挡掉「拖拽时选中界面文字」。

## 17. 快照版本号与迁移（补 §12）

### 为什么必须有版本号

`size: 0.034` 这个数字**自身的含义**是存档契约的一部分：v1 里它是「画布宽度的
3.4%」，v2 里是「安全区宽度的 3.4%」。改基准等于改契约，而存档是**旧契约的产物**。

没有版本号时，旧存档会被静默按新语义解释：用户升级后打开项目，排版全变（在
5244×2950 上同一份比率会从小字变大字或反之），而界面上没有任何线索说明为什么。

### v1 → v2 是**精确换算**，不是猜

v1 的语义确定（`渲染 px = 比率 × 画布宽度`），所以可以精确反解：

```
newRatio = ratio × 画布宽度 / 安全区宽度
```

实测（`verify:creative`）：v1 快照里 `headline.size = 0.034`、画布 5244×2950
（安全区 1402）→ 换算为 `0.034 × 5244 / 1402 = 0.127173` → 渲染
`0.127173 × 1402 = 178.296px`，与升级前的 `0.034 × 5244 = 178.296px`
**逐像素一致**。

同等重要的两条纪律：

1. **缺字段的条目不能换算。** `normalize` 会给缺失的 `size` 填**新基准**的默认值
   （0.08），如果迁移在 normalize 之后跑，它会把默认值也乘一遍 → 字号凭空大一倍多。
   因此迁移只作用于快照里**实际存在**的数值，且必须在 normalize **之前**。
2. **参考系只能是快照里当前的画布。** 换算后的比率在其他画布上的 px 会变 —— 但这是
   比率模型本身的性质（v1 也一样：同一份比率在不同画布上本来就渲染成不同 px），
   不是迁移引入的。迁移能保证的、也只需要保证的是「**打开时看到的画面不变**」。

### 迁移后必须立刻回写

`hydrate` 只改内存，localStorage 里仍是 v1。若不回写，每次打开都要重新迁移一遍 ——
结果虽然稳定（幂等），但设备上的存档**永远没有真正升级**：将来一旦删掉这段迁移代码，
那些 v1 存档就会被当成 v2 解释，排版照样突变。

因此 `usePersistence.ts` 的 `wireStore` 会比较存档里的 `version` 与 store 暴露的
`snapshotVersion`，不一致就**立刻 `save()`**（不等用户的下一次编辑）。

`verify:creative` 有对应断言（「迁移后写回的是 v2 快照」），以及最关键的幂等断言：
**二次刷新不会重复换算** —— 若换算没有版本门槛，字号会在每次刷新后翻 3.7 倍。

### 上界必须容得下迁移结果

`normalizeBrand` 的 clamp 上界是**推导出来的**，不能随手改小：迁移系数最大为
`5244 / 1402 ≈ 3.741`，v1 时代 logoSize / nameSize 的上界是 0.15 / 0.1，
所以迁移后的最大值为 0.561 / 0.374 → 上界取 **0.6 / 0.4**。
取小了会让老用户的 logo 在升级后莫名变小，而且没有任何提示。

### 一个命名陷阱

localStorage key 结尾的 `.v1`（`app-preview-studio.project.v1` /
`…creative.v1` / `…crop.v1`）**与快照里的 `version` 字段无关**。
前者是 key 的历史命名，**不能改**（改了用户已有项目就丢了）；后者是数据结构版本。
两者恰好都叫 v1，但改一个和改另一个是完全不同的操作。

### 验证

`verify:creative` 46 → 55 项，新增 9 条：坑位尺寸恢复 / 迁移基准 = 安全区宽度 /
比率精确换算 / **渲染字号与升级前一致** / 副标题与品牌一起换算 /
缺字段条目不被误放大 / 迁移后写回 v2 / **二次刷新幂等** / v2 快照不再被换算。

## 18. 修正：唯一一张图删不掉（裁剪工作台的删除出口）

### 现象

上传了唯一一张图，**没有任何办法把它删掉**：面板里的「🗑 删除」置灰。

### 根因

`stores/crop.ts` 的 `removeItem` 上有一道守卫：

```ts
// 移除条目；至少保留一个（列表为空时无处可拖入图片）
if (items.value.length <= 1) return false
```

面板按它算出 `canRemove = items.length > 1`，于是按钮在只剩一张时置灰。
**这条约束的理由不成立**：拖拽 / 粘贴是 `window` 级监听（`useImageUpload`），
不受列表长度影响；面板也一直有「＋ 导入图片」。空列表反而是最自然的初始状态。

真正的问题不是「能不能删」，而是**置灰且不解释**：用户看不到任何线索说明
为什么删不掉，只能判定为 bug。

### 修法

1. **`removeItem` 去掉守卫**，允许删到 0 条。0 条是合法状态：
   - `CropCanvas` 的 `item` 改为可选，空列表时只画**空画框**（比例仍然正确，预览不塌）
   - 画布中央沿用既有的空状态提示（「把成品图拖进来 · 或 ⌘V 粘贴 · 或在左侧导入」）
   - 列表区新增空状态块，导入按钮照旧可用
2. **`hydrate` 接受空列表**。它原先把 `items.length === 0` 视为无效快照，
   于是「删光 → 刷新」会冒回一张空位，用户会以为删除没生效。
3. **导出按钮在有图之前置灰**。`exportCropActive` / `exportCropAllSizes` 在没有图时
   直接 `return`，而按钮还能点 —— 这是同一类的「操作成功但界面无变化」。
4. **另外两个工作台仍要求 ≥1**，但理由不同且正当：它们的 `activeItem` 是
   所有设计面板的操作对象（主题 / 文案 / 版式 / 机型都以当前条目为宿主），
   0 条时整套面板没有目标，只能全部禁用，比置灰一个删除按钮更糟。
   该约束现在写在按钮的 `title` 上，不再「置灰且不说」。

### 顺带修掉的第二个问题：防抖窗口内的删除会丢

配置写回 localStorage 有 **400ms 防抖**，而验证脚本恰好撞上了它：删空后立刻
`reload`，回到页面时是**原来的 12 张** —— 删除丢了。

对用户来说这是「删掉的图自己回来了」。`wireStore` 现在在
